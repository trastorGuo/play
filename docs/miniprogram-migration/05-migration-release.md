# 数据迁移、部署与上线方案

## 1. 环境规划

| 环境 | 用途 | 数据 |
|---|---|---|
| local | 本地开发 | 构造数据 |
| test | 自动化与联调 | 每日重置 |
| staging | 真机、提审前验证 | 脱敏生产样本 |
| production | 正式服务 | 生产数据 |

每个环境使用独立的 MySQL、Redis、微信配置和域名。生产 AppSecret 不得出现在非生产环境。

## 2. CI/CD 流程

### Pull Request

```text
lint → typecheck → unit test → API integration test
→ OpenAPI validation → migration dry-run → build
```

### 主分支

```text
构建不可变镜像 → 漏洞扫描 → 部署 staging
→ smoke test → 人工批准 → production canary
→ 健康检查 → 扩大流量
```

小程序端：

```text
类型检查 → 单元测试 → 构建体验版 → 真机回归
→ 上传审核版本 → 微信审核 → 配置灰度 → 全量发布
```

## 3. 生产拓扑

```text
微信小程序
  └─ HTTPS/WSS 域名
      └─ Nginx / 云负载均衡
          ├─ NestJS API 实例 A
          ├─ NestJS API 实例 B
          └─ Outbox Worker
               ├─ MySQL 主库
               └─ Redis
```

初期用户量较小时可以单实例上线，但数据库、Redis 和备份必须独立持久化，应用容器不得保存业务数据。

## 4. 现有数据问题

迁移前必须处理：

- 旧用户 ID 来自浏览器字符串哈希，无法证明微信身份。
- 房间号采用“最大值 + 1”，可枚举且有并发风险。
- 余额为 Decimal，而小程序接口计划使用整数分。
- 写流水和改两方余额没有数据库事务。
- TypeORM 开启 `synchronize: true`。
- 旧交易用昵称冗余标识参与者，昵称变更会改历史记录。
- 旧管理 API 没有身份认证。

## 5. 数据迁移策略

采用“新表双轨 + 只读旧系统”，不要直接原地重构生产表。

### 第一次演练

1. 备份生产数据库并在隔离环境恢复。
2. 部署 v2 schema migration。
3. 将旧房间复制到 `rooms_v2`。
4. 为每个旧成员建立 `room_members_v2`，`user_id` 暂为空。
5. 金额按十进制字符串乘 100，禁止经过 JavaScript 浮点计算。
6. 将旧流水映射到新成员 ID。
7. 生成每房间的 `version` 和事件基线。
8. 对活跃旧成员生成一次性认领码。
9. 执行核对 SQL 和业务检查。
10. 输出迁移报告，不修改生产。

### 正式迁移

```text
T-7d  完成最终演练和恢复演练
T-1d  提醒旧网页即将进入只读
T-0   禁止旧系统新建和写账
      记录最后旧流水 ID
      数据库快照
      执行增量迁移
      运行一致性校验
      开启 API v2 写入
      发布小程序灰度
T+1d  复核房间和流水数量
T+7d  扩大灰度
T+30d 关闭旧网页业务入口
```

### 身份认领

- 旧房间只读查看不要求认领。
- 继续操作活跃旧房间必须认领对应成员。
- 每个旧成员生成一次性高熵认领码，后台只存哈希。
- 认领成功把 `room_members_v2.user_id` 绑定到微信内部用户。
- 认领码过期或遗失由管理员人工核实，不允许仅凭昵称认领。

## 6. 一致性校验

每次迁移必须输出：

```text
旧房间数 = 新房间数
旧成员数 = 新 legacy 成员数
旧流水数 = 新迁移流水数
逐笔 amount * 100 = amount_minor
每个房间 SUM(balance_minor) = 0
每个成员 balance_minor = 收款合计 - 付款合计
所有流水双方均属于同一房间
所有房主均存在对应 owner 成员
```

发现任何金额不一致时停止切换，不能自动“抹平”余额。差异必须输出房间号、成员和关联流水供人工确认。

## 7. 灰度方案

### 阶段 A：内部体验

- 仅开发、测试和产品账号。
- 使用 staging 数据。
- 验证登录、分享、扫码、后台切换和弱网。

### 阶段 B：生产白名单

- 选取新建房间用户，不接触旧数据。
- 监控 3 天，重点观察重复提交和 WebSocket。

### 阶段 C：旧数据认领

- 向少量活跃旧房间开放。
- 对照旧网页只读结果。

### 阶段 D：全量

- 小程序成为唯一写入口。
- 旧网页保留 30 天只读。

## 8. 回滚方案

### 应用回滚

- API 镜像保留最近 3 个稳定版本。
- 数据库 migration 必须向前兼容至少一个应用版本。
- 灰度异常时将流量切回旧 API 镜像。

### 小程序回滚

- 保留上一个稳定审核版本。
- 利用版本管理回退；服务端保持对上一小程序版本兼容。
- 服务端支持远程关闭实时通信、分享码、撤销等非核心功能。

### 数据回滚

- 上线后已经发生的新账目不能通过还原旧快照解决。
- 若 v2 写入有系统性错误，应立即进入只读维护模式。
- 修复后通过流水重放或补偿记录恢复，保留审计。
- 只有在确认没有任何新写入时才允许整库快照回退。

## 9. 备份与恢复

- MySQL 每日全量备份，15 分钟增量或 binlog 持续备份。
- 备份跨可用区保存，至少保留 30 天。
- 每季度执行恢复演练，记录 RPO/RTO。
- Redis 不作为账目备份来源。
- 部署前额外创建人工快照并验证可恢复。

## 10. 运维手册

### Redis 故障

- REST 记账继续可用。
- Outbox 保留未发布事件。
- 小程序进入 REST 轮询模式。
- Redis 恢复后补发事件并刷新在线状态。

### WebSocket 故障

- 关闭 WSS 功能开关。
- 小程序自动轮询。
- 不影响记账事务。

### 微信登录接口故障

- 已登录且 access token 有效的用户继续使用。
- 新登录显示服务繁忙并重试。
- 不使用伪造或匿名身份兜底。

### 余额不平告警

1. 立即禁止相关房间继续写入。
2. 导出该房间全部流水和成员余额。
3. 从流水重新推导余额。
4. 定位缺失、重复或部分提交记录。
5. 通过补偿 migration 修复，禁止直接手改余额。

## 11. 上线检查清单

- [ ] 微信小程序主体、名称、类目完成。
- [ ] request/socket/upload/download 合法域名配置正确。
- [ ] HTTPS/WSS 证书有效且支持完整证书链。
- [ ] 隐私政策和用户协议可访问。
- [ ] AppSecret 已进入密钥管理。
- [ ] 生产数据库 `synchronize` 已关闭。
- [ ] migration 和回滚脚本经过 staging 演练。
- [ ] 管理后台认证和审计开启。
- [ ] 限流、告警、日志脱敏开启。
- [ ] 数据库备份与恢复演练通过。
- [ ] 旧网页只读开关可用。
- [ ] 小程序上一稳定版本回退路径已验证。
