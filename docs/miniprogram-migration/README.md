# 多人牌局记账微信小程序迁移方案

> 版本：1.0
> 目标：把现有站点中的“多人打牌记账”拆分为可独立开发、审核、部署和运营的微信小程序。

## 1. 决策摘要

- 小程序使用 **uni-app + Vue 3 + TypeScript + Pinia**，便于团队延续现有 Vue 经验。
- 不使用 WebView，不直接复用 Element Plus 页面；保留业务流程，重写交互层。
- 后端保留 NestJS、MySQL、Redis，但新增 `/api/v2`，不让小程序直接调用旧接口。
- 登录改为 `wx.login -> code2Session -> 内部用户 -> access token/refresh token`。
- 写操作走 HTTPS REST；标准 WSS 只做订阅、心跳和变更通知。
- 金额统一使用整数分 `amountMinor`；记账必须在数据库事务中完成。
- Web 管理后台继续独立存在，并补充管理员认证、权限和审计。
- 老网页进入 30 天只读过渡期；匿名旧用户通过一次性认领码迁移身份。

## 3. V1 范围

### 必须交付

1. 微信静默登录与 token 刷新。
2. 创建房间、房间号加入、微信卡片加入、小程序码加入。
3. 设置房间昵称、查看成员和余额。
4. 给其他成员新增一笔记账。
5. 房间动态和完整流水。
6. 实时刷新、断线重连、REST 降级。
7. 撤销自己的记账，房主可处理超时撤销。
8. 房主关闭房间并查看最终结算。
9. 最近参与房间和历史只读房间。
10. 管理后台认证、查询和审计。

### V1 不做

- 微信支付、资金托管、充值、提现。
- 下注、赔率、抽成、随机奖励。
- 群聊、语音、图片消息。
- 好友关系和公开房间广场。
- 多端小程序同时发布。
- 离线记账后自动合并；断网时只允许浏览缓存。

## 4. 关键业务定义

- “金额”在产品文案中默认称为“分数”或“记账金额”，系统不承担真实支付。
- 一笔记录表示 `fromMember -> toMember` 的转移。
- 成员余额可为负数，房间内所有有效账目推导出的余额之和必须等于 0。
- 撤销不是删除原记录，而是新增一笔反向流水。
- 关闭后的房间永久禁止新增、修改和撤销，只允许查看。
- 房间号用于输入；邀请 token 用于分享鉴权，两者不能相互替代。

## 5. 非功能指标

| 指标 | 目标 |
|---|---|
| API 可用性 | 月度 99.9% |
| 普通查询 P95 | 小于 500 ms |
| 写操作 P95 | 小于 800 ms |
| 变更通知延迟 P95 | 小于 2 秒 |
| 重复记账 | 0 条，依靠幂等键保证 |
| 账目不平 | 0 个房间 |
| 单房间人数 | V1 最多 10 人 |
| 单房间流水 | 至少支持 10,000 条分页查询 |
| 恢复目标 RPO | 小于等于 15 分钟 |
| 恢复目标 RTO | 小于等于 2 小时 |

## 6. 交付边界

### 小程序团队

- 页面、组件、状态管理、请求层、WebSocket 管理器。
- 登录续期、场景值解析、分享、错误和弱网体验。
- 埋点、错误上报、版本兼容和真机测试。

### 后端团队

- 微信登录、API v2、权限守卫、事务记账、撤销、结算。
- WebSocket、Redis 广播、限流、审计、迁移脚本。
- 小程序码生成、管理后台认证和部署监控。

### 产品与测试

- 文案与审核材料、隐私政策、用户协议。
- 业务规则确认、验收用例、灰度名单与回滚决策。

## 7. 里程碑

| 里程碑 | 内容 | 建议时间 |
|---|---|---:|
| M0 | 规则冻结、交互稿、数据审计 | 3 天 |
| M1 | 登录、数据库迁移、API v2 骨架 | 5 天 |
| M2 | 创建/加入/房间/记账主链路 | 8 天 |
| M3 | 实时同步、分享、撤销、结算 | 6 天 |
| M4 | 迁移演练、真机测试、安全加固 | 7 天 |
| M5 | 提审、灰度、正式切流 | 5 天 |

双人研发加半职测试约 4～6 周；单人实施建议 6～8 周。

## 8. 上线门槛

- 所有写接口完成身份、成员关系和房间状态校验。
- 记账、撤销全部具备事务和幂等测试。
- 管理接口未登录返回 401，无权限返回 403。
- 完成生产数据备份和至少一次恢复演练。
- 分享卡片、小程序码、冷启动、前后台和弱网通过真机测试。
- 旧数据金额、流水数量和房间数量迁移核对一致。
- 微信审核文案中不出现下注、赌博、抽成或现金兑付承诺。
