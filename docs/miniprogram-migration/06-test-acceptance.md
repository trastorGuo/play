# 测试与验收方案

## 1. 测试分层

| 层级 | 范围 | 建议工具 |
|---|---|---|
| 单元测试 | 规则、金额、昵称、权限、事件版本 | Vitest/Jest |
| 数据库集成 | 事务、锁、幂等、约束、migration | Jest + 测试 MySQL |
| API 契约 | OpenAPI 请求响应与错误码 | Supertest |
| 小程序组件 | 表单、状态、金额显示 | uni-app 测试能力 |
| E2E | 创建到结算完整链路 | 微信开发者工具自动化 + 真机 |
| 性能测试 | 并发记账、查询、WebSocket | k6/Artillery |
| 安全测试 | 越权、重放、注入、限流 | 自动扫描 + 人工用例 |

## 2. 后端关键用例

### 登录

- 有效 code 首次登录创建内部用户。
- 同一微信用户重复登录返回同一内部用户。
- 无效、过期、已使用 code 返回认证错误。
- refresh token 轮换后旧 token 不可再次使用。
- 被禁用用户不能刷新或建立 WSS。

### 房间

- 创建房间同时创建 owner 成员。
- 并发创建不会产生重复房间号。
- 已在房间的用户重复加入恢复原成员，不增加人数。
- 第 11 名成员加入被拒绝。
- 房间内规范化昵称不能重复。
- 普通成员不能关闭房间。
- 房主未转让前不能离开。
- 关闭房间后所有写接口被拒绝。

### 记账

- 正常记账后付款方减少、收款方增加。
- 房间余额总和保持为 0。
- 0、负数、超上限、自己给自己均被拒绝。
- 目标成员不属于房间时被拒绝。
- 客户端伪造操作者或付款人字段无效。
- 相同幂等键并发提交只产生一笔流水。
- 数据库任一步骤失败时流水和余额全部回滚。
- Redis 故障不回滚已成功的账目，Outbox 保留事件。

### 撤销

- 操作者在允许时间内可撤销。
- 非房主超过时间不能撤销。
- 房主可以撤销有效流水。
- 同一流水只能撤销一次。
- 撤销生成反向流水，不能物理删除。
- 撤销后双方余额和总和正确。

### 权限

- 未登录调用业务接口返回 401。
- 非成员读取私有房间返回 403。
- 普通成员调用房主接口返回 403。
- 无管理员角色访问管理 API 返回 403。
- 枚举房间号不能获取成员和流水。

## 3. 并发测试

至少覆盖：

1. 同一用户双击提交同一幂等键。
2. 同一用户不同幂等键同时给两人记账。
3. A 给 B、B 给 A 同时记账。
4. 10 名成员同时发起 100 笔操作。
5. 记账与关闭房间同时发生。
6. 记账与目标成员离开同时发生。
7. 撤销与第二次撤销同时发生。

验收：无死锁遗留、无部分写入、无重复流水、余额总和为 0。可重试死锁事务，但同一请求总重试不超过 3 次。

## 4. WebSocket 测试

- 有效票据只能使用一次。
- 过期票据不能连接。
- 非成员不能订阅房间。
- 正常事件版本连续递增。
- 重复和乱序事件不污染客户端状态。
- 丢失事件后客户端通过版本差拉取快照。
- 断网、切网、前后台切换后自动恢复。
- WSS 不可用时切换 REST 轮询。
- Redis 重启后各实例恢复订阅。
- 长连接心跳和空闲关闭符合预期。

## 6. E2E 主链路

### E2E-01 新房间

```text
A 登录并创建房间
→ A 分享给 B
→ B 设置昵称并加入
→ A 给 B 记 20.00
→ 两端在 2 秒内显示 A -20.00、B +20.00
→ B 查看流水
→ A 关闭房间
→ 双方进入只读结算
```

### E2E-02 断线恢复

```text
A、B 在房间
→ B 断网
→ A 连续新增两笔记录
→ B 恢复网络
→ 自动重连并拉取快照
→ B 数据版本、余额和流水与服务端一致
```

### E2E-03 幂等

```text
A 提交记账时超时
→ 客户端使用原幂等键重试
→ 服务端返回第一次处理结果
→ 数据库只有一笔流水
```

### E2E-04 历史认领

```text
旧成员输入认领码
→ 绑定微信内部用户
→ 历史流水和余额保持不变
→ 认领码第二次使用失败
```

## 7. 性能目标

测试数据：1,000 个活跃房间、每房间 10 人、每房间 10,000 条流水。

| 场景 | 目标 |
|---|---|
| 登录 P95 | < 1,000 ms，不含微信上游长尾 |
| 房间快照 P95 | < 500 ms |
| 新增记账 P95 | < 800 ms |
| 流水翻页 P95 | < 500 ms |
| 结算查询 P95 | < 800 ms |
| 实时通知 P95 | < 2 s |
| API 错误率 | < 0.5% |
| 单实例并发 WSS | 通过实测确定并记录上限 |

性能测试不能绕过认证、权限和事务，否则结果无意义。

## 8. 安全验收

- [ ] 改 token 中的 userId 无法越权。
- [ ] 改 roomCode 不能读取非成员流水。
- [ ] 改 toMemberId 不能跨房间记账。
- [ ] 重放请求不产生重复流水。
- [ ] 分享 token 可撤销且不可从数据库明文泄露。
- [ ] 微信 code、OpenID、session key 不进入客户端日志。
- [ ] 管理员接口具备认证、授权、限流和审计。
- [ ] SQL/JSON/日志注入测试通过。
- [ ] 错误响应不包含堆栈、SQL 或内部密钥。
- [ ] 依赖漏洞扫描无阻断级问题。

## 9. 数据验收 SQL 思路

上线前后均检查：

```sql
-- 每个房间余额总和必须为 0
SELECT room_id, SUM(balance_minor) AS total
FROM room_members_v2
GROUP BY room_id
HAVING SUM(balance_minor) <> 0;

-- 不允许跨房间流水
SELECT lr.id
FROM ledger_records_v2 lr
JOIN room_members_v2 fm ON fm.id = lr.from_member_id
JOIN room_members_v2 tm ON tm.id = lr.to_member_id
WHERE fm.room_id <> lr.room_id OR tm.room_id <> lr.room_id;

-- 同一原流水不能有多条撤销
SELECT original_record_id, COUNT(*)
FROM ledger_records_v2
WHERE type = 'reversal'
GROUP BY original_record_id
HAVING COUNT(*) > 1;
```

所有查询必须返回空结果。

## 10. 最终验收标准

### 功能

- 创建、加入、分享、记账、撤销、结算和历史查询形成闭环。
- 所有定义的异常状态有明确反馈和恢复路径。
- 旧数据可以只读查看，符合条件的数据可以安全认领。

### 数据

- 无重复流水、无部分事务、无余额不平。
- 迁移前后房间、成员、流水和金额核对一致。
- 账目撤销保留完整审计链。

### 安全

- 客户端无法指定操作者身份。
- 所有房间和管理员接口完成服务端授权。
- 密钥、token、OpenID 和备注不出现在不安全日志。

### 稳定性

- WSS 故障不影响 REST 记账。
- 弱网和前后台切换后自动恢复权威数据。
- 告警、备份、恢复和回滚路径完成演练。

### 发布

- 微信体验版真机回归通过。
- 隐私政策、用户协议和审核材料齐全。
- 灰度指标满足门槛后才允许全量。
